# 02. 技術選定の比較

決定は Phase 1 の ADR-0002 で行う。ここは比較材料のみ。

## 前提

- データの正は **kintone**（レコード蓄積 / REST API）。
- あなたの既存スキル: Electron、kintone API。
- 候補 A / B / D は「現場端末での素早い入力」、候補 C / E は「事務 PC での管理業務」が中心。

## フロントエンド形態

| 形態 | 向く候補 | 長所 | 短所 |
|---|---|---|---|
| Electron（デスクトップ） | E、A（既設 Windows PC がある場合） | 既存スキル、ローカル保存・オフラインが容易、Mission Bridge と統合可 | タブレット・スマホでは動かない |
| PWA / Web（ブラウザ） | A、B、D | タブレット・スマホ・PC で同じ画面、配布が URL だけ | ホスティング先が必要。オフラインは Service Worker 実装が要る |
| kintone カスタマイズ JS | B、C、D | 追加インフラ不要、認証は kintone 任せ | UI 自由度が低い、現場入力には重い |

**目安**: 現場入力が主なら PWA、事務・管理が主なら Electron、最小工数で試すなら kintone カスタマイズ JS。

## 共通の技術要素（形態に依らず）

| 要素 | 第一候補 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型で kintone フィールドコードのミスを防ぐ |
| ビルド | Vite | Electron / PWA どちらにも使える |
| UI | React | 部品化しやすく、Electron / PWA で共通化できる |
| kintone 通信 | `@kintone/rest-api-client` | 公式。認証・一括操作・リトライが揃う |
| テスト | Vitest | Vite と相性がよく設定が少ない |
| 設定 | `.env` + `.env.example` | 認証情報を Git に入れない |

## kintone 側の設計指針

- 1 アプリ = 1 種類の事実（例: 「停止記録」「停止理由マスタ」）。集計は kintone のグラフか、アプリ側で行う。
- フィールドコードは英小文字スネークケース（`line_id`, `stop_reason`, `started_at`）で固定し、型定義をコードと共有する。
- API トークンはアプリ単位・最小権限（追加のみ / 閲覧のみ）で分ける。
- 429 / 5xx はリトライ（指数バックオフ）を必須にする。

## 判断に必要な未確認事項

- 現場端末の種類と OS。
- kintone 環境で API トークン発行・アプリ作成ができるか。
- PWA を選ぶ場合のホスティング先（社内サーバ / クラウド）の可否。
