# 01. ロードマップ

期間は「1 人・業務の合間に週 5〜8 時間」を仮定した目安。実態に合わせて ADR で更新する。

| Phase | 名称 | 目安 | 主な成果物 | 完了条件 |
|---|---|---|---|---|
| 0 | 構想決定 | 1 週 | 決定シート、ADR-0001 | 候補 1 つ、対象・成功指標・端末が確定 |
| 1 | 要件・設計 | 1〜2 週 | 画面一覧、kintone アプリ設計、ADR-0002（技術選定） | 画面 3 枚以内と kintone フィールド定義が固定 |
| 2 | MVP 実装 | 2〜4 週 | 動くアプリ、kintone アプリ、セットアップ手順 | 想定ユーザーが手順書だけで 1 件登録できる |
| 3 | 現場試行 | 2〜4 週 | 利用ログ、フィードバック一覧、改修リスト | 成功指標の計測値が出る。継続可否を判断 |
| 4 | 展開・運用 | 継続 | 展開手順、運用ルール、バックアップ方針 | 2 つ目の対象（ライン / 部署）で稼働 |

## Phase 0: 構想決定（今ここ）

1. `docs/00_concept-candidates.md` の決定シートを埋める。
2. 不明点（端末、kintone 権限）を確認する。
3. ADR-0001 を書く。

## Phase 1: 要件・設計

- **ユーザーストーリー** を 5〜10 本に絞る（「○○として、△△したい、なぜなら□□」）。
- **画面**: 一覧 / 入力 / 集計 の 3 枚を上限に手描きワイヤーで固定。
- **kintone 設計**: アプリ 1〜2 個。フィールドコード・型・必須・選択肢を表に落とす。
- **技術選定**: `docs/02_tech-stack-options.md` を基に ADR-0002 で決定。
- **非機能**: オフライン時の扱い、認証（API トークン or ログイン）、ログ保存先。

## Phase 2: MVP 実装

実装順は「データが貯まる経路」を最優先にする。

1. kintone アプリ作成、テストレコード投入。
2. kintone REST クライアント（認証・登録・取得）とその自動テスト。
3. 入力画面（1 画面）。
4. 一覧・簡易集計（1 画面）。
5. セットアップ手順書と `.env.example`。

**やらないこと（MVP では明示的に除外）**: 権限管理の細分化、他システム連携、通知、多言語。

## Phase 3: 現場試行

- 対象は決定シートの「最初の対象」に限定。
- 週 1 回、利用件数と困りごとを 15 分で回収する。
- 改修は「記録が止まる原因」を最優先、見栄えは後回し。

## Phase 4: 展開・運用

- 2 つ目の対象へ展開する前に、設定を外出し（ライン名・理由マスタを kintone 側で管理）。
- バックアップ: kintone 側が正。アプリ側にはキャッシュ以上のデータを持たせない。

## リスクと先回り

| リスク | 兆候 | 先回り策 |
|---|---|---|
| 記録が続かない | 2 週目で件数半減 | 入力 3 タップ以内、入力必須項目を 2 つ以下に |
| kintone API 制限 | 429 エラー | 一括登録 API を使い、リトライを実装 |
| 端末が用意できない | Phase 0 で確定しない | 候補 B へ切替、または既設 PC のブラウザ運用 |
| 要件が膨らむ | 画面 4 枚目の話が出る | 「MVP ではやらないこと」に追記し Phase 4 送り |
