# 実装計画：レクチャー資料 → 部品ライブラリ → Mission Bridge への適用

## 結論
- デモ（01〜86）のうち、業務アプリの骨格になる10機能を **`ui-kit/`（依存なし・ESモジュール）に切り出し、テスト付きで実装済み**（Phase 0 完了）
- Mission Bridge の画面ごとの適用（Phase 2）は、**実物の画面構成が不明なため未着手**。下の「確認事項」が埋まり次第、対応表を確定して着手する
- 演出系（E層）は最後。採否は実機のフレーム時間で決める

## 前提と不明点
| 項目 | 状態 |
|---|---|
| Mission Bridge のリポジトリ | このセッションからは不可視。見えるのは `Reiri0135678/-`（本リポジトリ）と `Reiri0135678/arpoi-field-app` のみ。後者が該当するかは **不明** |
| 画面一覧・遷移 | 不明 |
| 既存の技術構成（素の JS か、フレームワーク使用か、TypeScript か） | 不明。ui-kit は素の ESM なので、どちらでも import できる |
| kintone 連携の方式（REST 直叩き / 独自プロキシ / 認証方法） | 不明。ui-kit は通信層を持たず、`send` 関数を注入する設計にして依存を切っている |
| 対象端末の性能（現場PC・タブレット） | 不明。E層の採否に影響 |

## 方針
1. **デモはデモのまま残す**（教材・仕様の確認用）。本番コードはデモをコピーせず `ui-kit/` を import する
2. **通信・保存は注入**する。`ui-kit` は `fetch` も kintone も知らない。`send`, `storage`, `isOnline` を外から渡す
3. **状態は1つのオブジェクトに集約**し、画面はそれを描画する（75・80・81 の作法）。Undo・永続化・同期がすべてこの前提で動く

## Phase 1：Mission Bridge 側の受け入れ準備（要リポジトリ）
1. 現状の画面一覧と、各画面で「重い・使いにくい」と感じている操作を列挙する
2. ビルド構成に ESM が通るか確認（Electron renderer なら通常そのまま import 可能）
3. kintone 通信層を `send(job)` の形に揃える（`PUT /k/v1/record.json` を job として表現し、revision を持たせる）
4. 状態オブジェクトの置き場所を決める（画面ごとの `store`）

**受け入れ基準**：既存画面を壊さずに `ui-kit` を 1 つ import して動くこと（最初は `hotkeys.js` の Ctrl+S が最小）
