業務アプリでのアクセシビリティは「障害対応」だけでなく「マウスを持ち替えずに入力できる」「現場の暗い場所・老眼でも読める」「動きで酔わない」という作業効率と安全の話。ここでは自分で検査できる道具と、各デモがどう対応しているかをまとめる。

A1キーボードだけで操作できるか フォーカス順の可視化

マウスなしで全機能に届くか。Tab の順番が見た目の順と一致しているか、フォーカスが見えるか、閉じ込められて抜けられない箇所がないか。下のボタンで、このページ内の「フォーカスできる要素」に番号を振って順路を可視化する。

操作：「フォーカス順を表示」→ 番号が見た目の順に並んでいるか確認。その後 Tab で実際に辿る。

A2読み上げに何が伝わるか アクセシブルネームと role

スクリーンリーダーは「役割（role）」と「名前（accessible name）」を読む。アイコンだけのボタンは名前が空になる。aria-label か視覚的に隠したテキストで名前を与える。下の検査は、ページ内のボタン・リンクで名前が空のものを列挙する。

A4非同期結果の通知 aria-live の polite / assertive

保存完了やエラーを画面の隅に出しても、読み上げユーザーには伝わらない。aria-live 領域にテキストを書くと自動で読み上げられる。polite は今の読み上げが終わってから、assertive は割り込む（エラー用）。領域は最初から存在させ、中身だけ変える。

操作：ボタンで通知。スクリーンリーダー（Windows: ナレーター Win+Ctrl+Enter、macOS: VoiceOver Cmd+F5）を起動して聞く。

A7canvas と 3D の代替経路 見えない中身をどう伝えるか

<canvas> の中身は支援技術から完全に見えない。画素があるだけで、要素も文字も無いためである。3D ビューア（Z層）・グラフ・図面エディタはすべてこれに当たる。やることは3つ。①canvas 自体をフォーカスできる操作対象にする（tabindex="0" ＋ role ＋ aria-label）②キーボードだけで一巡できるようにする（矢印キーで対象を順に選ぶ）③選択結果や測定値を canvas の外の文字として出す（aria-live）。「見て触る」前提の UI ほど、代替経路を後から足せないので最初に決める。

操作：下の枠を Tab で選び、矢印キーで部品を順に選ぶ。Enter で確定、Esc で解除。読み上げに渡る文字が右に出る。マウスでも同じことができる。
