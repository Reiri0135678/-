117埋め込みでログインが切れる 3rd party Cookie / CHIPS / Storage Access API模擬

「PC では見えるのに、iPhone だと iframe の中がログイン画面になる」の原因。ブラウザは埋め込まれた別サイトの Cookie を、トップレベルのサイトごとに分離する。2026年時点の状況：Chrome は 3rd party Cookie の廃止を撤回して継続、Safari・Firefox はブロックを継続。つまり環境によって挙動が違う状態が続く。対処は3つ：CHIPS（Cookie に Partitioned を付け、トップレベルごとに別の入れ物として持つ）、Storage Access API（ユーザー操作を起点に許可を求める）、そしてそもそも iframe をやめる（114 の③④）。

操作：この端末の判定と、3方式の比較を表示する。

CHIPS：埋め込み用の Cookie はこう出す（サーバ側） 
Set-Cookie: session=…; Secure; SameSite=None; Partitioned; Path=/
Storage Access API：埋め込まれた側から、ユーザー操作を起点に頼む 
button.onclick = async () => {
  if (await document.hasStorageAccess()) return use();
  await document.requestStorageAccess();     // クリックの中でしか呼べない

119OAuth 2.1 と PKCE 認可コード + PKCE（S256）実動

2026年の標準形。OAuth 2.1 では PKCE が必須で、implicit フロー（トークンを URL で受け取る）は廃止。仕組み：①ランダムな code_verifier を作り ②その SHA-256（code_challenge）だけを認可画面へ渡す ③戻ってきた認可コードと verifier を一緒に送る。途中でコードを盗まれても、verifier を知らなければトークンに交換できない。アクセストークンはメモリに置く（localStorage は XSS で読まれる）。リフレッシュトークンは自前サーバからの HttpOnly Cookie にする。

操作：実際に WebCrypto で verifier / challenge を生成し、模擬の認可サーバとやりとりする。攻撃者がコードだけ盗んだ場合も試せる。

120Electron での認証 システムブラウザ + safeStorage模擬

デスクトップアプリではアプリ内に認証画面を埋め込まないのが原則（利用者が本物のドメインを確認できないため、相手のサービスに拒否されることも多い）。システムブラウザを開き、ループバック（http://127.0.0.1:port）かディープリンク（myapp://）で戻す。トークンは safeStorage で OS の鍵に紐づけて暗号化し、renderer には渡さない（12 の構成）。

main.js（要点だけ） 
const { shell, safeStorage } = require('electron');
const server = http.createServer(...).listen(0);                 // ① 空きポートで受け口を用意
const redirect = `http://127.0.0.1:${server.address().port}/cb`;
shell.openExternal(authUrl(redirect, codeChallenge));            // ② システムブラウザで開く
// ③ /cb に来た code と verifier をトークンに交換（119）
const enc = safeStorage.encryptString(refreshToken);             // ④ OS の鍵で暗号化して保存
// renderer には「ログイン済みか」だけ返し、トークン自体は渡さない
やること理由
システムブラウザで開く利用者がドメインと鍵マークを確認できる。相手サービスの規約でも要求されることが多い
ループバック or ディープリンクアプリに確実に戻すため。ループバックはポート固定にしない
safeStorage平文の JSON に置くと、端末を触れる人が全員読める
renderer に渡さないrenderer は Web と同じ危険（XSS）を持つ。トークンは main に閉じる（121）

122レート制限と再試行 429・バックオフ・冪等キー実動

外部 API は必ず絞られる（kintone も 1 アプリあたりの同時実行数・秒間リクエスト数に上限がある。具体的な数値は相手の仕様書で確認すること＝ここでは断定しない）。上限に当たると 429 Too Many Requests が返り、多くは Retry-After ヘッダで「何秒待て」と教えてくる。やることは3つ。①すぐ再試行しない（待ち時間を倍々にする＝指数バックオフ）②ジッター（ゆらぎ）を足す（全端末が同時に再開すると再び詰まる＝雪崩）③冪等キーを付ける（送信は成功したが応答が届かなかったとき、二重登録を防ぐ）。

操作：同じ模擬 API（先頭2件しか通らない）に 6 件送る。3つの方式で結果と所要時間を比べる。

-
やること理由やりがちな失敗
Retry-After を読むサーバが正解の待ち時間を知っている無視して独自の待ち時間で押し続ける
指数バックオフ混雑が続くほど間隔を空ける固定間隔で叩き続けて上限を延長させる
ジッター全端末の再開時刻をばらす秒ちょうどに全員が再送＝雪崩
冪等キー応答が届かなかった再送で二重登録しない再試行のたびに新しい ID を作る
上限を決める永久に再試行すると詰まりが伝播する無限リトライ＋画面が固まる
同時実行数を絞るそもそも 429 を出さないのが最善1000 件を Promise.all で一気に投げる

画面側の見せ方：再試行中は「送信中（再試行 2 回目）」と状態を出す。黙って待つと利用者が二重に押す。最終的に失敗したら 79 の再送キュー（オフライン待ち行列）に積み、後で自動再開する。アクセシビリティ上も、この状態は aria-live="polite" で伝える（A6）。

この処理は部品として切り出してある：ui-kit/retry.js。retry(fn, {retries, baseMs, shouldRetry, onRetry}) ／ withRetry(fn, opts)（冪等キーを固定して渡す）／ httpError(res)（Retry-After を読んだ Error を作る）／ createLimiter(n)（同時実行数を絞る＝そもそも 429 を出さない）。fetch の例：

import { withRetry, httpError, createLimiter } from '../../ui-kit/index.js';

const post = withRetry(async (body, { signal, idempotencyKey }) => {
  const res = await fetch('/api/orders', { method: 'POST', signal,
    headers: { 'content-type': 'application/json', 'Idempotency-Key': idempotencyKey },
    body: JSON.stringify(body) });
  if (!res.ok) throw httpError(res);              // 429/5xx は再試行、4xx はそのまま失敗
  return res.json();
}, { retries: 4, onRetry: i => setStatus(`再試行 ${i.attempt} 回目（あと ${Math.round(i.delay / 100) / 10} 秒）`) });

const limit = createLimiter(3);                   // 一気に投げない
await Promise.all(rows.map(r => limit(() => post(r, { idempotencyKey: `order-${r.id}` }))));

123Webhook の受け側 署名検証・リプレイ・冪等実動

相手のサービスから「起きたこと」を押し込んでもらう仕組み。受け口は誰でも叩ける URL なので、次の3つが必須。①署名検証（本文と共有鍵の HMAC が一致するか。ここは WebCrypto で実際に計算する）②時刻の確認（古い正しい署名の使い回し＝リプレイを弾く）③冪等処理（相手は「届いたか不明」なら再送する。同じイベント ID を二度処理しない）。さらに順序は保証されない前提で、イベント内の版番号や更新時刻で新旧を判断する。

操作：正しい配送・改ざん・古い時刻・再送を送り分け、受け口の判定を見る。

-
前提受け側の作り
誰でも叩ける署名検証を通るまで本文を信用しない。URL を秘密にすることは対策にならない
再送されるイベント ID で冪等化。処理済みでも 200 を返す（4xx/5xx を返すと再送が続く）
順序は保証されない版番号・更新時刻で新旧を判断。「後から来た＝新しい」と考えない
相手はタイムアウトする受け取ったら即 200。重い処理はキューに積んで非同期で回す
取りこぼすWebhook だけに頼らず、定期的な差分取り込み（照合）を併走させる

ブラウザは Webhook を受けられない（外から到達できる URL が要る）。受け口はサーバか、社内に置いた常駐プロセスになる。Electron アプリに直接届けたい場合は、いったんサーバで受けて 124 の SSE/WebSocket で流すか、アプリ側から定期取得する。

124反映方式の選び方 ポーリング／SSE／WebSocket実動

「他の人の更新をどう画面に出すか」の3択。ポーリング＝一定間隔で問い合わせる。最も簡単で、どんな相手にも使える（kintone のように Webhook しか無い相手でも成立）。SSE（EventSource）＝サーバから一方向に流し続ける。実装が軽く自動再接続つき。WebSocket＝双方向。カーソル共有や共同編集はこれが要る。迷ったらポーリングから始め、遅延と無駄が問題になってから上げる。
