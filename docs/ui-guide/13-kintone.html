kintone 連携リファレンス UI操作との対応

⌂ 入口カタログElectronD
デモの中で「kintone ならこう」と書いた箇所を、API 側の制約とセットでまとめる。UI の作りは API の上限で決まる（1回で取れる件数、1回で更新できる件数、リビジョン）。数値は執筆時点の把握であり、必ず公式 REST API リファレンスで確認すること。このページは参照用で、コードは実行されない。

0. 呼び出しの置き場所（Electron の場合）

renderer から kintone へ直接 fetch すると、オリジン（file:// や app://）からの CORS で拒否される。main プロセスで通信し、IPC で結果を返す（12 の構成）。トークンも main にだけ置ける。

// main.js
ipcMain.handle('kintone:request', async (e, { method, path, params, body }) => {
  const url = new URL(path, `https://${SUBDOMAIN}.cybozu.com`);
  if (method === 'GET' && params) url.search = new URLSearchParams(params);
  const res = await net.fetch(url, { method, headers: { 'X-Cybozu-API-Token': token(), 'Content-Type': 'application/json' }, body: body && JSON.stringify(body) });
  const json = await res.json();
  if (!res.ok) throw Object.assign(new Error(json.message || res.statusText), { code: json.code, status: res.status, errors: json.errors });
  return json;
});

1. 一覧の取得 ← 21 ページネーション / 23 仮想スクロール / 71 大規模グリッド

取得は GET /k/v1/records.json。1回の limit は最大 500、offset は上限あり（大きな値で拒否される）。数千件を超えるならカーソル API（作成→取得を繰り返す）か、$id でソートして「前回の最後の id より大きい」を条件にする方法。取り切ったデータは 23/71 の仮想スクロールで描く（DOM は表示分だけ）。

// 方式A: offset/limit（件数が少ない・ページ番号 UI に向く）… 21 の pager と同じ
GET /k/v1/records.json?app=1&query=order by $id asc limit 500 offset 0

// 方式B: id 基準（offset 上限を避ける。全件取得に向く）
let last = 0, all = [];
while (true) {
  const { records } = await api({ method: 'GET', path: '/k/v1/records.json', params: { app: 1, query: `$id > ${last} order by $id asc limit 500` } });
  all.push(...records); if (records.length < 500) break; last = records.at(-1).$id.value;
}
// 方式C: カーソル API（POST /k/v1/records/cursor.json で作成 → GET で繰り返し取得 → 使い終わったら DELETE）

UI 側：取得中は 22 のスケルトン、取得済み件数と総件数（totalCount: true を付けると返る）を 40 の進捗で出す。

2. 更新とリビジョン ← 57 楽観的更新 / 78 競合解決

レコードは $revision を持つ。PUT 時に revision を付けると、サーバ側が進んでいればエラーで拒否される（省略または -1 で無視）。これが 78 の「楽観ロック」。手順：①開いた時の revision を保持 ②保存時に付けて PUT ③拒否されたら最新を GET して 3方向マージ（ui-kit/merge.js）→ 再 PUT。

// 1件更新
PUT /k/v1/record.json  { app: 1, id: 1001, revision: 5, record: { 数量: { value: '120' } } }
// 拒否された場合（HTTP 409 系。エラーコードは公式で確認）→ 78 のフロー
const server = await api({ method: 'GET', path: '/k/v1/record.json', params: { app: 1, id } });
const { merged, conflicts } = threeWayMerge(base, mine, flatten(server.record));
if (conflicts.length) { /* ダイアログで選ばせる */ }
await api({ method: 'PUT', path: '/k/v1/record.json', body: { app: 1, id, revision: server.record.$revision.value, record: toKintone(merged) } });

57 の楽観的更新と組み合わせるなら：画面は先に変え、PUT 失敗（競合含む）で巻き戻してから 78 へ。

3. 一括更新 ← 76 バッチ操作

PUT /k/v1/records.json は 1回 最大 100 件（POST 追加・DELETE 削除も同様）。101 件以上は 76 のようにチャンク分割し、チャンクごとに進捗を進める。1回のリクエスト内は全件成功か全件失敗（原子的）なので、「部分失敗」はチャンク単位で起きる。複数種類の操作をまとめて原子的に行いたいときは bulkRequest（1回の中に複数リクエスト、上限あり）。

for (const chunk of chunks(changes, 100)) {
  try { await api({ method: 'PUT', path: '/k/v1/records.json', body: { app: 1, records: chunk.map(c => ({ id: c.id, revision: c.revision, record: c.record })) } }); done += chunk.length; }
  catch (err) { failed.push({ chunk, err }); }           // 76: 失敗チャンクだけ再試行
  progress.value = done;
}

4. 検索 ← 74 検索の型

サーバ検索は query パラメータ（like、in、and/or、order by）。入力のたびに投げないよう 74 のデバウンス（250ms 以上）を入れ、前のリクエストが返る前に次が出たら古い結果を捨てる（連番で判定）。取得済みデータの絞り込みなら手元で ui-kit/search.js。

let seq = 0;
const run = debounce(async (text) => {
  const my = ++seq;
  const res = await api({ method: 'GET', path: '/k/v1/records.json', params: { app: 1, query: `品名 like "${escapeQuery(text)}" order by $id desc limit 100` } });
  if (my !== seq) return;                                 // 古い応答は捨てる
  render(res.records);
}, 300);

5. オフラインと再送 ← 79

現場端末で通信が切れる前提なら、更新を ui-kit/offline-queue.js に積む。job には app, id, revision, record を入れ、送信時に revision 不一致なら 78 のフローへ回す（課題12）。Electron では main 再起動後もキューが残るよう、storage にファイル保存の実装を渡す。
