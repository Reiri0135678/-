# 構想メモ(壁打ち記録)

更新: 2026-09-05

## 目的

品質管理室が各部門から**紙ベース**で受け取っている検査依頼をデジタル化する。
これが最優先タスク。

## 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| アプリ形態 | **ブラウザ + 社内 LAN の Node.js 同期サーバー** | 多人数同時編集が必須要件。Electron 単体+ローカル保存では成立しない(v0.1 で採用した Electron は廃止) |
| 同時編集 | tldraw sync(`@tldraw/sync` / `@tldraw/sync-core`)を自前サーバーで運用 | 競合解決・差分配信を自作しない |
| ボードの単位 | 部門ごと 1 ボード(初期値: 品質管理室 / 製造1課 / 製造2課)+ 任意追加 | まず複数人で触って要件を固めるため |
| ユーザー識別 | users.json による名前+パスワード(無ければ自己申告) | 社内アカウント(M365 等)連携は auth.ts の差し替えで対応 |
| kintone 連携 | サーバー側から REST API。shape id を外部キーに作成/更新 | ボードが正、kintone は蓄積・検索・他システム連携用 |
| Mission Bridge との関係 | **埋め込む**(WebContentsView / webview)。Mission Bridge のログインユーザーを共有鍵経由で QC Board に代理ログイン | ユーザー指定。QC Board は独立 Web アプリのまま保ち、Mission Bridge は表示とユーザー受け渡しだけ担う |
| キャンバス | tldraw SDK を採用 | 描画エンジン自作を避け、UI/UX のカスタマイズ(独自ツールバー・独自図形)に工数を集中 |
| 開発順序 | ①キャンバス → ②リスト・画像一覧 → ③kintone 連携 | ユーザー指定 |
| 技術構成 | Vite + React + TypeScript(client)/ Node.js + express + ws(server) | Mission Bridge と技術資産を共有しやすい構成 |

## 現在の実装(v0.4 プロトタイプ)

- **依頼一覧のスプレッドシート**(下部ドロワー): セル直接編集、列見出しで並べ替え、全文検索、状態フィルタ、CSV 出力(BOM 付き、Excel 対応)
- **図面・写真ギャラリー**(サイドバー): サムネイル一覧、クリックでズーム、紐付け先カード数の表示
- **カードと図面の紐付け**: カードから「図面を紐付け」→ ギャラリーかキャンバスの画像をクリック。カードに 📎 件数、関連図面のサムネイルから移動
- **kintone 連携**: 「kintone へ送信」でカードをレコードとして作成/更新(shape id を外部キーに)。レコード番号をカードに書き戻し全員に同期。設定は config/kintone.json、モックで検証済み
- **認証と閲覧権限**: users.json による名前+パスワード。役割 admin / member / viewer。viewer はサーバー側で読み取り専用。users.json が無ければオープンモード

- **サイドバーの依頼リスト**: ボード上の依頼カードを状態別件数つきで一覧表示。行クリックでカードへズーム
- **依頼カードの編集フォーム**: カードを選択するとサイドバーに状態・品番・ロット・数量・依頼者・依頼日・備考の入力欄。編集は即時に全員へ同期
- **依頼者・依頼日の自動記録**: カード作成時にユーザー名と当日を記録。既存ボードは props マイグレーションで補完
- **図面・写真の取り込み**: 画像をドラッグ&ドロップするとサーバーに保存され、全員に表示(E2E で検証済み)

- **多人数同時編集**: 2 ブラウザ間で図形が双方向に同期、相手のカーソルと名前が見える(E2E で検証済み)
- **ボード一覧と作成**: 名前入力 → ボード選択。新規ボード作成可
- **サーバー永続化**: 最後の人が抜けたら JSON スナップショット保存。次回開いた時に復元
- 独自縦型ツールバー(既定ツールバーを差し替え、日本語ラベル)
- 不要な既定 UI(メインメニュー、ページメニュー、共有、デバッグ)を非表示
- 独自図形「検査依頼カード」(`request-card`): 部門・品番・ロット・数量・ステータス
  - props は将来 kintone レコード項目に 1:1 で写せる粒度
- tldraw アイコン・フォントをバンドル同梱(オフライン動作)

## 未決事項・要確認

- [ ] 同期サーバーを置く社内サーバー(Node.js 常駐可能な PC/サーバーの有無)
- [ ] 社内アカウント(Microsoft 365 等)でのログインが必要か(必要なら OIDC 化)
- [ ] kintone 側の受け皿アプリ(フィールド構成)と API トークンの発行
- [ ] kintone → ボードの逆方向同期が必要か(現状はボード → kintone の一方向)
- [ ] 紙の依頼書の項目一覧(現物の写真 or スキャンが欲しい)
- [ ] 依頼の流れ(受付→割当→検査→結果返却のどこまでをスコープに含めるか)
- [ ] 依頼元部門の環境(PC/タブレットの有無、kintone アカウントの有無)
- [ ] 1日あたりの件数、依頼部門数
- [ ] 画像一覧の「画像」の正体(図面、現物写真、依頼書スキャン)
- [ ] キャンバスの主用途(図面への注釈 / 手書き依頼書の再現 / カード配置による進捗管理)
- [ ] tldraw のライセンス条件(本番利用時のキー要否・費用)
- [ ] Mission Bridge の実際の技術構成

## 次の候補タスク

1. 実データでの検証: 紙の依頼書に合わせたカード項目の見直し(現状は仮の項目)
2. kintone 実環境での接続確認(現状はモック検証のみ)
3. ボード一覧に「誰が今見ているか」と最終更新を表示
4. 通知(新規依頼・状態変更を kintone 通知や Teams などへ)
5. 監査ログ(誰がいつ何を変えたか)

## 構想の補足と改善点(2026-09-05 レビュー)

v0.4 まで作った上で、構想として抜けている点・弱い点を業務面と技術面に分けて整理する。
「決」は既に決めた前提、「要」はユーザーの判断が必要、「案」は私の提案。

### A. 業務面

| # | 論点 | 現状 | 補足・改善案 | 区分 |
|---|---|---|---|---|
| A1 | **受付番号** | shape id(機械的な文字列)のみ | 人が口頭・紙・電話で参照できる連番(例 `QC-2026-0001`)をサーバーで採番。kintone の外部キーもこれに寄せる | 案 |
| A2 | **状態遷移** | 未受付→受付→検査中→完了 の 4 段階 | 実務には「保留」「差戻し(情報不足)」「不合格→再検査」「中止」がある。遷移ルール(誰がどの状態へ動かせるか)を決める | 要 |
| A3 | **担当・納期・優先度** | 項目なし | 担当検査員、希望納期、優先度(通常/至急)を追加。一覧の並べ替え・色分けの軸になる | 案 |
| A4 | **検査結果の記録** | スコープ外(第2段階) | 合否、測定値、判定者、判定日、報告書添付。第1段階でも「合否」だけは持たせると依頼者への返却が完結する | 要 |
| A5 | **依頼元の入力口** | ボードに直接カードを置く | 依頼者にホワイトボードは自由度が高すぎる。**「依頼フォーム」画面(項目入力+図面添付だけ)**を別途用意し、送信するとボードにカードが現れる形が定着しやすい。タブレット・スマホからも使える | 案 |
| A6 | **紙の依頼書との対応** | 項目は仮 | 現物の依頼書の項目を写すのが最優先。スキャン画像をカードに紐付ける「紙併存期間」の運用も決める | 要 |
| A7 | **通知** | なし | 新規依頼(品質管理室へ)、状態変更・完了(依頼者へ)。kintone 通知、メール、Teams のいずれか。kintone 経由なら追加実装が最小 | 要 |
| A8 | **ボードの肥大化** | 部門ごと 1 ボードに溜まり続ける | 完了カードの自動アーカイブ(一定日数後にボードから外し一覧・kintone には残す)、または月次でボードを切る | 案 |
| A9 | **過去依頼の検索** | ボード内の一覧検索のみ | 横断検索・集計は kintone 側が主戦場。kintone のレコードからボードのカードへ戻れるリンク(URL)を持たせる | 案 |
| A10 | **正データの所在** | ボードが正、kintone は蓄積 | kintone 側で編集されると食い違う。「kintone は読み取り専用」か「双方向同期」かを決める。前者を推奨(実装と運用が単純) | 要 |
| A11 | **図面の扱い** | 画像のみ、版管理なし | PDF 図面はサーバーで画像化して取り込む。図面は機密のため閲覧権限・持ち出し(ダウンロード)制限を検討 | 要 |
| A12 | **品質記録としての要件** | 変更履歴なし | ISO 9001 等の記録として使うなら「誰がいつ何を変えたか」の履歴が必須。カード削除の扱い(物理削除でなく取消状態)も決める | 要 |
| A13 | **数量・単位** | 文字列 | 数量は数値+単位に。集計(日別件数、部門別、リードタイム)の前提になる | 案 |
| A14 | **Mission Bridge との関係** | 埋め込み+代理ログインを実装済み | ホスト側イベント(ready / board-opened / card-selected)で Mission Bridge の他機能と連動できる。QC Board 側の users.json は不要になる | 決 |
| A15 | **認証** | users.json のパスワード | 人数が多いなら M365 等の社内アカウント(OIDC)へ。少人数なら現状で十分 | 要 |

### B. 技術面

| # | 論点 | 現状 | 補足・改善案 | 区分 |
|---|---|---|---|---|
| B1 | **tldraw ライセンス** | 未取得(透かし表示) | 本番前に必須。費用と条件を確認 | 要 |
| B2 | **保存方式** | ボードごと JSON ファイル。最後の人が抜けた時+変更 1 秒後 | サーバー異常終了で直近 1 秒が失われる程度だが、世代管理が無い。`@tldraw/sync-core` の SQLite ストレージへ移行し、日次バックアップ(data/ のコピー)を運用に組み込む | 案 |
| B3 | **変更履歴・監査ログ** | なし | 同期サーバーはセッション単位で差分を受け取れる(`onAfterReceiveMessage` / `onCommittedChanges`)。ユーザー名と紐付けて追記型ログに残す。A12 の実装基盤 | 案 |
| B4 | **通信の暗号化** | 社内 LAN の平文 HTTP | LAN 内限定なら許容範囲だが、Cookie に Secure が付かない。リバースプロキシ(Caddy 等)で HTTPS 化すると設定 1 行で済む | 要 |
| B5 | **サーバーの常駐** | 手動起動 | Windows なら NSSM でサービス化、Linux なら systemd。自動再起動と起動時ログ | 案 |
| B6 | **画像の肥大化** | 削除されたカード・画像のファイルが残る | 参照されないアップロードの定期削除(GC)。上限 50MB/ファイルも用途に合わせ見直す | 案 |
| B7 | **kintone 連携の詳細** | 一方向、shape id を外部キー | カードの複製(コピペ)は別レコードになる。削除はレコードに反映されない。A1 の受付番号をキーにし、削除は「取消」状態で送る | 案 |
| B8 | **タブレット表示** | PC 前提のレイアウト | サイドバー・ドロワーを折りたたみ式に。A5 の依頼フォームはモバイル優先で作る | 案 |
| B9 | **同時接続規模** | 数十人程度を想定 | tldraw sync は 1 ルーム数十人で問題なし。全社規模なら Cloudflare Durable Objects 版も選択肢 | 決 |
| B10 | **オフライン** | サーバー停止中は編集不可 | 業務上許容できるか。許容できないなら B5 の自動再起動と B2 のバックアップで十分 | 要 |

### C. 優先順位の提案

**構想として今決めるべきこと**(実装に先立つ): A6 → A2 → A5 → A10 → A12 → B1
これらが決まると、カード項目・状態・入力口・履歴の設計が固まり、以後の手戻りが消える。

**次の実装順(案)**:
1. 受付番号の採番 + 担当・納期・優先度(A1, A3)
2. 依頼フォーム画面(A5)。依頼者はボードを開かなくてよくなる
3. 変更履歴ログ(B3)と削除の取消化(A12)
4. SQLite 保存 + バックアップ手順(B2)
5. 完了カードのアーカイブ(A8)
6. 通知(A7)
7. PDF 図面の取り込み(A11)
